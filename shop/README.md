# Shop — راهنمای ویرایش امن (قرارداد اتصال به اپ)

این پوشه (سایت فروش) از اپلیکیشن **کاملاً جدا** است. می‌توانید طراحی، متن،
عکس، انیمیشن و صفحات را آزادانه تغییر دهید — کد اپ (`index.html`) دست نمی‌خورد.
فقط ۵ نقطه‌ی اتصال زیر را حفظ کنید:

---

## 🔗 نقاط اتصال (این‌ها را نشکنید)

### ۱. آدرس‌های لینک
| از | به | کجا |
|---|---|---|
| دکمه‌های Buy Now | `/shop/checkout.html?plan=basic\|professional` | `shop/index.html` |
| دکمه Start Free | `/index.html` (اپ) | `shop/index.html` |
| دکمه Open the app | `/index.html` | `shop/checkout.html` |
| برگشت به فروشگاه | `/shop/` | `shop/checkout.html` |

اگر صفحه‌ی checkout را جابه‌جا کردید، در اپ هم ثابت `SHOP_URL` (ابتدای
`index.html`) را به‌روز کنید — همین یکی.

### ۲. شناسه‌ی پلن‌ها — دقیقاً این سه مقدار
```
basic  ·  professional  ·  club
```
این‌ها باید بین سه جا یکی باشند:
- `shop/index.html` (لینک‌های Buy Now)
- `shop/checkout.html` (شیء `PLANS`)
- بک‌اند اپ: `netlify/lib/billing.mjs` → `PLANS`

اگر پلن جدید اضافه می‌کنید (مثلاً `studio`)، باید هر سه جا اضافه شود؛
وگرنه checkout خطای `bad-plan` می‌دهد.

### ۳. قرارداد API پرداخت
`checkout.html` این درخواست را می‌فرستد:
```js
POST /shop/api/checkout
body: { planId, email }
پاسخ موفق: { ok: true, coupons: ["PRO-XXXXXXXXXX", …] }
```
- **فرانت فروشگاه هرگز کلید `ADMIN_API_KEY` را ندارد** — صدور کوپن فقط در
  `shop/api/checkout.mjs` (سمت سرور) انجام می‌شود.
- درگاه واقعی (زرین‌پال/…) فقط داخل `shop/api/checkout.mjs` وصل می‌شود:
  تابع `simulatePayment()` را با verify درگاه جایگزین کنید. فرانت و اپ
  هیچ تغییری نمی‌خواهند.
- پاسخ باید همیشه `coupons` (آرایه) بدهد؛ فرانت اولین عضو را نمایش می‌دهد.

### ۴. پارامتر `?plan=`
دکمه‌های خرید داخل اپ کاربر را با `?plan=professional` به checkout می‌فرستند.
`checkout.html` این پارامتر را می‌خواند و پلن را از پیش انتخاب می‌کند —
این منطق را حذف نکنید.

### ۵. localStorage مشترک
| کلید | کاربرد |
|---|---|
| `coach-os-locale` | هماهنگی زبان سایت ↔ checkout ↔ اپ (fa/en) |
| `coach-os-email` | ایمیل خریدار — اپ آن را در فرم ثبت‌نام/ورود پیش‌پر می‌کند |
| `coach-os-coupon` | آخرین کد فعال‌سازی صادرشده — اپ آن را در فیلد کدِ ثبت‌نام/ورود و کادر کوپن (تنظیمات → حساب) پیش‌پر می‌کند و بعد از ریدیم موفق پاک می‌شود |

### ۶. فعال‌سازی خودکار در اپ (ثبت‌نام/ورود با کد)
اپ هنگام ثبت‌نام/ورود یک فیلد **اختیاری** «کد فعال‌سازی» دارد که از
`coach-os-coupon` پیش‌پر می‌شود؛ کد در همان درخواست signup/login سمت سرور
ریدیم می‌شود و پلن بلافاصله فعال است (کدِ فعال هر اشتراک در پروفایل اپ —
تنظیمات → حساب — نمایش داده می‌شود). ریدیم دستی از تب حساب هم همچنان کار می‌کند.
کد نامعتبر/مصرف‌شده هرگز مانع ساخت اکانت یا ورود نیست — فقط هشدار می‌دهد و کد
برای retry در تب حساب می‌ماند.

حذفشان مشکلی ایجاد نمی‌کند (فقط راحتی کاربر کم می‌شود)، ولی نامشان را
تغییر ندهید اگر هماهنگی زبان را می‌خواهید.

## ✅ آزاد به تغییر (بدون هیچ ریسکی برای اپ)
- کل CSS، فونت‌ها، رنگ‌ها، انیمیشن‌های 3D
- متن‌ها و ترجمه‌ها (شیء `FA` در هر صفحه جدا است)
- عکس‌ها و لوگو در `assets/`
- افزودن صفحات جدید (بلاگ، تماس، FAQ…)
- تغییر قیمت‌های نمایشی — فقط با قیمت واقعی بک‌اند هماهنگ نگه دارید
  (`netlify/lib/billing.mjs` فقط سقف شاگردان را می‌داند؛ مبلغ در
  `shop/api/checkout.mjs` → `PRICES` است)

## 🧪 تست بعد از هر تغییر فروشگاه (۲ دقیقه)
1. `/shop` باز می‌شود؟
2. Buy Now → checkout با پلن درست باز می‌شود؟
3. پرداخت آزمایشی → کد صادر شد؟
4. کد در اپ ریدیم می‌شود؟ (تنها تستی که اپ را هم درگیر می‌کند)
5. دکمه‌های خرید داخل اپ (تنظیمات → حساب) هنوز به checkout می‌روند؟
