# Shop — راهنمای ویرایش امن (قرارداد اتصال به اپ)

این پوشه (سایت فروش) از اپلیکیشن **کاملاً جدا** است. می‌توانید طراحی، متن،
عکس، انیمیشن و صفحات را آزادانه تغییر دهید — کد اپ (`index.html`) دست نمی‌خورد.
فقط ۵ نقطه‌ی اتصال زیر را حفظ کنید:

---

## 🔗 نقاط اتصال (این‌ها را نشکنید)

### ۱. آدرس‌های لینک
| از | به | کجا |
|---|---|---|
| دکمه‌های Buy Now | `/shop/checkout.html?plan=basic\|professional` | `shop/index.html` |
| دکمه Start Free | `/index.html` (اپ) | `shop/index.html` |
| دکمه Open the app | `/index.html` | `shop/checkout.html` |
| برگشت به فروشگاه | `/shop/` | `shop/checkout.html` |

اگر صفحه‌ی checkout را جابه‌جا کردید، در اپ هم ثابت `SHOP_URL` (ابتدای
`index.html`) را به‌روز کنید — همین یکی.

### ۲. شناسه‌ی پلن‌ها — دقیقاً این سه مقدار
```
basic  ·  professional  ·  club
```
این‌ها باید بین سه جا یکی باشند:
- `shop/index.html` (لینک‌های Buy Now)
- `shop/checkout.html` (شیء `PLANS`)
- بک‌اند اپ: `backend/lib/billing.mjs` → `PLANS`

اگر پلن جدید اضافه می‌کنید (مثلاً `studio`)، باید هر سه جا اضافه شود؛
وگرنه checkout خطای `bad-plan` می‌دهد.

### ۳. قرارداد API پرداخت
`checkout.html` این درخواست را می‌فرستد:
```js
POST /shop/api/checkout
body: { planId, email }
پاسخ موفق: { ok: true, coupons: ["PRO-XXXXXXXXXX", …] }
```
- **فرانت فروشگاه هرگز کلید `ADMIN_API_KEY` را ندارد** — صدور کوپن فقط در
  `shop/api/checkout.mjs` (سمت سرور) انجام می‌شود.
- درگاه واقعی (زرین‌پال/…) فقط داخل `shop/api/checkout.mjs` وصل می‌شود:
  تابع `simulatePayment()` را با verify درگاه جایگزین کنید. فرانت و اپ
  هیچ تغییری نمی‌خواهند.
- پاسخ باید همیشه `coupons` (آرایه) بدهد؛ فرانت اولین عضو را نمایش می‌دهد.

### ۳‌.۱ قرارداد ثبت‌نام فروشگاه (signup)
صفحه‌ی checkout (در همان یک کلیکِ پرداخت، وقتی فیلد رمز پر شده باشد) و
`account.html` (تب «ساخت حساب») این درخواست را می‌فرستند:
```js
POST /shop/api/account/signup
body: { name, email, password, coupon? }   // coupon اختیاری
پاسخ موفق: { ok, token, coach, workspace, access, billing, quota, redeemed, redeemError? }
خطاها: 400 {error:'bad-email'|'bad-name'|'weak-password'} · 409 {error:'email-taken'}
```
- **جریان یکمرحلهای:** فیلد رمز در فرم خرید اختیاری است — پرشده = خرید + ساخت
  اکانت + فعالسازی در یک کلیک (دکمه به «Pay & create account» تغییر میکند)؛
  خالی = فقط خرید کد (برای تمدید یا کسی که قبلاً حساب دارد). اعتبارسنجی رمز
  **قبل از** پرداخت انجام میشود تا سفارش پرداختشده بدون اکانت باقی نماند.
- این endpoint یک **پروکسی** به `/api/auth/signup` اپ است (سرور-به-سرور) —
  کلید و منطق در فرانت نیست. IP خریدار هم فوروارد می‌شود تا محدودیت نرخ اپ
  به‌ازای هر خریدار اعمال شود، نه برای کل فروشگاه.
- اگر `coupon` معتبر باشد در همان درخواست ریدیم می‌شود و `billing.status`
  برابر `active` برمی‌گردد (دوره آزمایشی هرگز شروع نمیشود). کد نامعتبر مانع
  ساخت حساب نیست — `redeemError` برگردانده میشود.
- اگر ایمیل قبلاً ثبت شده باشد (409)، خرید و کد سالم میمانند و فقط هشدار
  کهربایی «وارد شو و کد را در تنظیمات → حساب ریدیم کن» نمایش داده میشود.
- توکن پاسخ هم برای اپ (`co-auth`) و هم برای صفحه حساب (`coach-os-shop-token`)
  ذخیره میشود؛ «Open the app» مستقیم وارد حسابتان می‌کند.

### ۴. پارامتر `?plan=`
دکمه‌های خرید داخل اپ کاربر را با `?plan=professional` به checkout می‌فرستند.
`checkout.html` این پارامتر را می‌خواند و پلن را از پیش انتخاب می‌کند —
این منطق را حذف نکنید.

#### ۴.۱ پلن `trial` (ثبت‌نام تریال ۱۴ روزه — بدون پرداخت)
دکمه‌ی «Start Free» سایت فروشگاه به `/shop/checkout.html?plan=trial` می‌رود —
**نه** مستقیم به اپ. در این حالت فرم checkout به یک فرم ثبت‌نام خالص تبدیل
میشود:
- رمز عبور **اجباری** است (لیبل «Password» بدون «اختیاری») و دکمه
  «Start free trial / شروع آزمایش رایگان» است؛ نوت درگاه پرداخت مخفی میشود.
- درگاه و کوپن کاملاً دور زده میشوند — فقط `POST /shop/api/account/signup`
  (بدون `coupon`) صدا زده میشود و تریال ۱۴ روزه سمت سرور توسط
  `/api/auth/signup` شروع میشود (`TRIAL_DAYS` در `auth-shared.mjs`).
- صفحه موفقیت بدون کد فعال‌سازی است: «Account created — your 14-day free
  trial is active» + «Open the app» (توکن در `co-auth` ذخیره شده).
- ایمیل تکراری (409) → پیام «This email already has an account — sign in
  instead.» روی فرم؛ چیزی از دست نمیرود.
- سوییچ پلن روی همان صفحه (trial ↔ پولی) لیبل‌ها را دوطرفه عوض میکند —
  متن‌ها از طریق `setT` (که `data-k` را هم بهروز میکند) ست میشوند تا
  تغییر زبان آنها را بازنویسی نکند.

### ۵. localStorage مشترک
| کلید | کاربرد |
|---|---|
| `coach-os-locale` | هماهنگی زبان سایت ↔ checkout ↔ اپ (fa/en) |
| `coach-os-email` | ایمیل خریدار — اپ آن را در فرم ثبت‌نام/ورود پیش‌پر می‌کند |
| `coach-os-coupon` | آخرین کد فعال‌سازی صادرشده — اپ آن را در فیلد کدِ ثبت‌نام/ورود و کادر کوپن (تنظیمات → حساب) پیش‌پر می‌کند و بعد از ریدیم موفق پاک می‌شود |
| `co-auth` | توکن نشست اپ — بعد از signup در فروشگاه نوشته میشود تا «Open the app» مستقیم وارد شود |
| `coach-os-shop-token` | توکن نشست صفحه حساب فروشگاه |

### ۶. فعال‌سازی خودکار در اپ (فقط ثبت‌نام — ورود با کد نیست)
اپ هنگام **ثبت‌نام** یک فیلد اختیاری «کد فعال‌سازی» دارد که از `coach-os-coupon`
پیش‌پر می‌شود؛ کد در همان درخواست signup سمت سرور ریدیم می‌شود و پلن بلافاصله
فعال است. **ورود فقط با ایمیل و رمز عبور است** — فرم ورود فیلد کد ندارد و
بک‌اند هم کوپن را در login نادیده می‌گیرد (کد مصرف نمیشود). تمدید/ریدیم دستی
از تب حساب انجام می‌شود: تنظیمات → حساب → کوپن. کد نامعتبر/مصرف‌شده هرگز مانع
ساخت اکانت نیست — فقط هشدار می‌دهد و کد برای retry در تب حساب می‌ماند.

حذفشان مشکلی ایجاد نمی‌کند (فقط راحتی کاربر کم می‌شود)، ولی نامشان را
تغییر ندهید اگر هماهنگی زبان را می‌خواهید.

## ✅ آزاد به تغییر (بدون هیچ ریسکی برای اپ)
- کل CSS، فونت‌ها، رنگ‌ها، انیمیشن‌های 3D
- متن‌ها و ترجمه‌ها (شیء `FA` در هر صفحه جدا است)
- عکس‌ها و لوگو در `assets/`
- افزودن صفحات جدید (بلاگ، تماس، FAQ…)
- تغییر قیمت‌های نمایشی — فقط با قیمت واقعی بک‌اند هماهنگ نگه دارید
  (`netlify/lib/billing.mjs` فقط سقف شاگردان را می‌داند؛ مبلغ در
  `shop/api/checkout.mjs` → `PRICES` است)

## 🧪 تست بعد از هر تغییر فروشگاه (۲ دقیقه)
1. `/shop` باز می‌شود؟
2. Buy Now → checkout با پلن درست باز می‌شود؟
3. پرداخت آزمایشی → کد صادر شد؟
4. کد در اپ ریدیم می‌شود؟ (تنها تستی که اپ را هم درگیر می‌کند)
5. دکمه‌های خرید داخل اپ (تنظیمات → حساب) هنوز به checkout می‌روند؟
